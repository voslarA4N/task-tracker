## Warnings

### WR-01: Re-rendered send form silently re-confirms newer attachment versions (WR-02 bypass)

**File:** `app/Controllers/InvoiceDelivery.php:257-262, 296, 337-411` (`submit()` / `rejected()`), `app/Views/invoices/_delivery_form.php:88-91`
**Issue:** `submit()` loads a fresh `$draft` at POST time. Every rejection except `attachments_changed` then re-renders `_delivery_form` from that fresh draft. The affected cases are 422 validation errors (`invalid_address`, `no_recipients`, `empty_content`, `too_long`, `invalid_subject`, `sender_invalid`) and the 502 `smtp_failed` "retry" form. The hidden `attachment_versions[...]` inputs are built from `$draft['attachments']`, so they now carry the latest versions, not the ones the owner posted.

In `sendLocked`, `validate()` (step 2) runs before `loadAttachments()` (step 5). So this sequence:

1. Open the form with report v1.
2. The report is regenerated to v2 (another tab or device).
3. Submit with a typo in the address. The response is 422 and the form now holds `report=2`.
4. Fix the address and send.

The result is that v2 is mailed and the "document was regenerated in the meantime" alert never appears. The same happens after an SMTP failure: "Skúsiť znova" sends whatever is latest at the moment of the failure. The only visible change is the 12-character sha prefix. This is exactly the "send bytes the owner did not knowingly confirm" situation that WR-02 was meant to close.

**Fix:** Check the confirmation in the controller before any other validation, and never re-issue a confirmation the user did not see with the alert:
```php
// in submit(), right after $values / the request_key check
$confirmed = $this->confirmedVersions();
$latest    = array_column($draft['attachments'], 'version', 'kind');

if ($confirmed !== [] && $confirmed != $latest) { // keys may differ in order
    return $this->panel('invoices/_delivery_form', 409, $draft, $values, [], lang('Deliveries.errorAttachChanged'), $kind);
}
```
Alternatively, have `rejected()` render the hidden inputs from the posted `confirmedVersions()` for all non-`attachments_changed` reasons. Then a stale confirmation still trips the 409 on the next submit. Add a feature test: regenerate, post with a bad address (expect 422), post again with a valid address, and expect 409 with no send.

## Info

### IN-01: `attachments_changed` path calls `draft()` without a guard, and the call is redundant

**File:** `app/Controllers/InvoiceDelivery.php:397-402`
**Issue:** `(new InvoiceMailer())->draft(...)` can throw `SendRejected` (`not_found`, or `not_sendable` if the invoice was cancelled or credited between the two reads). The exception escapes `rejected()` and the user gets a 500 instead of the 404 used elsewhere. The re-read is also unnecessary. `submit()` already loaded `$draft` at POST time, after the regeneration that caused the 409. The only way the versions can differ is another regeneration between that read and `send()`.
**Fix:** Drop the re-read, or wrap it: `try { $draft = ...->draft(...); } catch (SendRejected) { throw PageNotFoundException::forPageNotFound(lang('Invoices.notFound')); }`.

### IN-02: `Clock::parseInstant` still accepts impossible dates and a trailing newline

**File:** `app/Libraries/Platform/Clock.php:38-46`
**Issue:** The docblock and the fix report say impossible input throws. In practice, `'2026-02-31 10:00:00+01'` is parsed as `2026-03-03T10:00:00+01:00`, because PHP rolls day overflow over and the regex only bounds digit counts. The regex also has no `D` modifier, so `"...+01\n"` matches. Inputs come from PostgreSQL, so the real impact is low, but the method's contract is not met.
**Fix:** Add `/D`, and reject overflow by round-trip or warnings. For example, after construction:
```php
$errors = DateTimeImmutable::getLastErrors();
if ($errors !== false && ($errors['warning_count'] > 0 || $errors['error_count'] > 0)) { throw new InvalidArgumentException(...); }
```
Add the `2026-02-31` case to `provideParseInstantRejectsNonAbsolute`.

### IN-03: Legacy window lives in code, not data

**File:** `app/Database/Migrations/2026-11-04-000002_CreateInvoiceRegenWindows.php:15-29`, `app/Libraries/Invoicing/InvoiceRegenWindows.php:22, 69-80`
**Issue:** Invoices issued before the migration have no row, and `attach()` computes `created_at + LEGACY_HOURS` on every read. The invariant "every issued invoice has a frozen window" therefore cannot be checked in the DB. If someone edits the constant later, already-issued legacy invoices silently get a different window. The phase is not deployed yet, so a backfill is cheap now.
**Fix:** In `up()`, after creating the table:
```sql
INSERT INTO invoice_regen_windows (invoice_id, hours, regen_until, created_at)
SELECT id, 72, created_at + interval '72 hours', created_at FROM invoices WHERE origin = 'issued';
```
Keep the code fallback only as a fail-closed safety net, or drop it.

### IN-04: Forms opened before deploy get a misleading "regenerated" message

**File:** `app/Libraries/Delivery/InvoiceMailer.php:424-428`, `app/Language/*/Deliveries.php` (`errorAttachChanged`)
**Issue:** A send sheet that was already open, or restored by the PWA from before this deploy, posts no `attachment_versions`. The send is rejected (correct), but the message says the document "was regenerated in the meantime", which is not true. It is harmless but may confuse the owner.
**Fix:** Optionally distinguish `$confirmed === null` (form missing confirmation) from a version mismatch, or reword the message to "the attachments changed or the form is outdated".

### IN-05: Missing `document_settings` row surfaces as a raw 500 at issuance

**File:** `app/Libraries/Invoicing/InvoiceRegenWindows.php:43`, `app/Libraries/Invoicing/InvoiceIssuer.php:65-82`, `app/Libraries/Invoicing/CreditNoteIssuer.php:63-89`

Neither issuer maps it, so the exception reaches the controller unhandled. The rollback is correct (no number gap), and failing loudly was the intent, but there is no log context and no user message.
