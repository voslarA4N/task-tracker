## Summary

This re-review covers the gap-closure changes from plans 12.1-09 (ZIP cleanup, CR-01) and 12.1-10 (payment-only report label WR-01, client sort expression WR-02, redundant loop IN-01, decision id IN-05).

The `AccountantBundle::build()` cleanup is now exception-safe:
- `$closed` is set before `close()`.
- The discard path runs inside `try/catch (Throwable)`.
- `unlink` is suppressed.
- The two new integration tests use a real `ZipArchive` subclass to cover both `close()` returning false and `close()` throwing. They assert the exact exception class and that `writable/exports/*` ends up empty.

The `ReportCalculator` payment-only label now picks the newest paid invoice by `(issue_date, id)`. `issue_date` is a `YYYY-MM-DD` string, so the comparison works lexicographically. Clients that have in-period invoices keep the D-03 label. `InvoiceQueries` builds the client sort expression from `ClientNameSql` at runtime, and a unit test pins it.

One gap remains. A realistic `close()` failure arrives as an `ErrorException`, because CI4 converts the libzip warning. The controller does not catch `ErrorException`, so the user still gets an unhandled 500 instead of `Bundle.errorBuild`. That case is exactly what `testCloseThrowingLeavesNoFile` models. Two minor test and robustness notes follow.

## Warnings

### WR-01: `ErrorException` from a failed bundle build still escapes `Accountant::download()` as an unhandled 500

**File:** `app/Controllers/Accountant.php:54-72` (with `app/Libraries/Export/AccountantBundle.php:84-128`)
**Issue:** The new `catch (RuntimeException $e)` only handles the exceptions that `build()` throws explicitly ("Cannot finalize zip archive.", "Cannot open zip archive.", "Cannot read temporary bundle file."). The failures most likely in practice are PHP warnings, which CI4's error handler turns into `\ErrorException`. That exception extends `\Exception`, not `\RuntimeException`. Examples:
- libzip failing to write or rename on `close()` (disk full, permissions)
- `mkdir()` failing on `writable/exports`
- `tempnam()` falling back to the system temp dir, which emits a notice
- `file_get_contents()` failing

Plan 09 explicitly models this case ("a warning that CI4 turns into ErrorException", `testCloseThrowingLeavesNoFile`). Its threat model T-12.1-09-03 claims "controller logs the message before rendering errorBuild". For `ErrorException` that is not true: it bypasses all three catch blocks and the user gets the framework's generic 500 page instead of the localized `Bundle.errorBuild` alert with the preview. Cleanup is now correct, so no file leaks. The unhandled-500 part of the original CR-01 remains, though, and no feature test exercises the controller error path at all.
**Fix:** Also catch `ErrorException` and keep the plan's rule of not catching `Throwable`/`Error`:
```php
} catch (RuntimeException | \ErrorException $e) {
    log_message('error', 'Accountant bundle build failed: {message}', ['message' => $e->getMessage()]);

    return $this->page($in, ['alertText' => lang('Bundle.errorBuild')] + $this->previewData($in), 'reports/accountant/index', 500);
}
```
Alternatively, wrap I/O failures in `build()` into a `RuntimeException`, with the original as `previous`. Add a feature test that injects a failing bundle, for example through a service or factory seam, and asserts status 500 with the `Bundle.errorBuild` text.

## Info

### IN-01: `testEverySortKeyResolves` cannot fail for a missing `SORT_SQL` entry

**File:** `tests/unit/Invoicing/InvoiceQueriesSortTest.php:28-33` (with `app/Libraries/Invoicing/InvoiceQueries.php:42-49`)
**Issue:** `sortColumn()` falls back to the default column for any unknown key. If a new key is added to `InvoiceFilter::SORTS` but not to `SORT_SQL`, the method returns `i.issue_date` and `assertNotSame('', ...)` still passes. The test name promises coverage it does not give. In that situation the list would silently sort by issue date. Also, if `DEFAULT_SORT` is ever changed to a key that is neither `'client'` nor in `SORT_SQL`, `sortColumn()` recurses forever, because the fallback calls itself with the same key.
**Fix:** In the test, assert that every non-`client` key from `SORTS` exists in `SORT_SQL` (via reflection on the constant), or assert that `col($key) !== col(DEFAULT_SORT)` for every key other than `DEFAULT_SORT`. In the code, replace the recursive fallback with `self::SORT_SQL[InvoiceFilter::DEFAULT_SORT]`, or throw a `LogicException` when it is missing.

### IN-02: Unsorted `use` block in the bundle test

**File:** `tests/integration/Export/AccountantBundleTest.php:17-20`
**Issue:** `Closure`, `ErrorException` and `RuntimeException` were inserted before `Config\Services`, which breaks the alphabetical import order used in the rest of the file. `php-cs-fixer` / devkit `ordered_imports` will flag this.
**Fix:** Move the three imports to their alphabetical positions, or run the fixer.
