# Phase 12.1: Code Review Report

## Narrative Findings (AI reviewer)

## Summary

The snapshot client name rollout (`ClientNameSql`) is consistent across the list, detail, payments, delivery, overdue, bundle, and report read paths. The alias whitelist means the SQL fragment cannot be injected. The report-period bounds (2000-01..2100-12) are applied in the month view, the export endpoints, and the accountant bundle. The prev/next links are guarded so they can no longer throw at the edges.

There is one real defect in the new ZIP cleanup code in `AccountantBundle::build()`. When `ZipArchive::close()` fails, the `finally` block throws a `ValueError`. That error replaces the original exception and skips the temp-file unlink. I reproduced this with PHP 8.3 CLI.

There is also a smaller labelling inconsistency in `ReportCalculator`: the client label for a client that only has payments in the period does not follow the "latest snapshot" rule that the docblock says applies.

## Critical Issues

### CR-01: The ZIP cleanup in `finally` throws `ValueError` after a failed `close()`, which hides the real error and leaves the temp file behind

**File:** `app/Libraries/Export/AccountantBundle.php:111-128`
**Issue:** If `$zip->close()` at line 110 fails (disk full, write error, or a warning that CI4 turns into `ErrorException`), `$closed` stays `false`. PHP's `ZipArchive::close()` always sets the internal handle to NULL, even when it fails. The `finally` block then calls `$zip->unchangeAll()` on a closed archive, and that throws `ValueError: Invalid or uninitialized Zip object`. The `@` on the following `close()` does not help, because `unchangeAll()` throws first and `@` does not suppress exceptions anyway. The consequences:
1. The original `RuntimeException('Cannot finalize zip archive.')` or `ErrorException` is replaced by a `ValueError`.
2. The code after it, `if (is_file($tmp)) unlink($tmp);`, never runs, so a partial bundle with invoice PDFs stays in `writable/exports/`. This is a data-leak and disk-growth risk, which is exactly what this change was meant to prevent.
3. `Accountant::download()` only catches `BundleRejected` and `DocumentIntegrityError`, so the user gets an unhandled 500 instead of `Bundle.errorBuild`.

I reproduced this on PHP 8.3 CLI: after `close()` returns `false`, `unchangeAll()` throws `ValueError: Invalid or uninitialized Zip object`.

**Fix:** Mark the archive as closed before calling `close()` (the attempt always ends the handle), and make cleanup unable to throw:
```php
$closed = true;            // close() always invalidates the handle, success or not
if (! $zip->close()) {
    throw new RuntimeException('Cannot finalize zip archive.');
}
...
} finally {
    if ($opened && ! $closed) {
        try {
            $zip->unchangeAll();
            @$zip->close();
        } catch (\Throwable) {
            // handle already gone; fall through to unlink
        }
    }
    if (is_file($tmp)) {
        @unlink($tmp);
    }
}
```
Add an integration test that forces `close()` to fail (for example, remove the exports directory before closing) and asserts that a `RuntimeException` is thrown and the temp file no longer exists.

## Warnings

### WR-01: A client with only payments in the period gets the oldest snapshot name, not the latest

**File:** `app/Libraries/Reporting/ReportCalculator.php:196` (with `labels()` at 131-149)
**Issue:** The docblock (D-03) says the client label is taken from the snapshot of the most recent issued document. `labels()` only covers clients that have invoices with `turnover_date` inside the period. A client that only has payments in the period is labelled in `addPayments()` via `??=`, using the first matching payment row. Those rows are ordered `p.invoice_id, p.paid_on, p.id`, so the label comes from the snapshot of the lowest invoice id, which is the oldest name. Example: a client is renamed between two invoices and both are paid in November with no new invoicing. The November report shows the old name, while the month in which the newer invoice was issued shows the new name. This contradicts the documented rule, and `testPaymentOnlyClientUsesSnapshotName` does not catch it because it only has one invoice.
**Fix:** In `addPayments`, keep the label from the newest invoice instead of the first row. For example, track `issue_date` and `id` per client and replace the label when a row has a later `(issue_date, id)`. Alternatively, extend `labels()` with a `UNION` over invoices that have a payment in the period, ordered the same way, and add a test that has two differently named paid invoices.

### WR-02: The client sort expression is a copied literal that no test checks for equality

**File:** `app/Libraries/Invoicing/InvoiceQueries.php:18-19`
**Issue:** `SORT_SQL['client']` hard-codes the same `COALESCE(NULLIF(f.snapshot->'client'->>'name', ''), c.name)` string that `ClientNameSql::snapshotName('f')` returns. The comment says a sort test pins it. `testSortByClientUsesSnapshotName` only checks the order of three rows, though. If `ClientNameSql` changes (for example to add `trim()` or a different fallback), the displayed `client_name` and the sort key will drift apart without any test failing. That would bring back the "screen shows X but sorting uses Y" mismatch this phase set out to remove.
**Fix:** Resolve the expression at runtime instead of in a constant, for example `$col = $filter->sort === 'client' ? ClientNameSql::snapshotName('f') : self::SORT_SQL[...]`. Alternatively, add a unit test that asserts `SORT_SQL['client'] === ClientNameSql::snapshotName('f')` via reflection.

## Info

### IN-01: The label overwrite loop after `addPayments` is redundant

**File:** `app/Libraries/Reporting/ReportCalculator.php:89-93`
**Issue:** Every client that `labels()` returns also has an invoice row in `$rows`, so its name was already set from `$labels` at line 74 before `addPayments` runs. The loop only re-applies names that are already there. It suggests a fix for payment-only clients that it does not actually make (see WR-01).
**Fix:** Remove the loop, or replace it with the WR-01 fix.

### IN-02: An empty or whitespace snapshot name silently falls back to the live name for issued documents

**File:** `app/Libraries/Invoicing/ClientNameSql.php:25`
**Issue:** `NULLIF(..., '')` makes an issued invoice with a corrupted or blank snapshot name show the current `clients.name`, which can be mutable. A whitespace-only name (`'  '`) is not caught at all and shows up blank. For issued documents, a missing snapshot name is an integrity anomaly and should not be papered over silently.
**Fix:** Use `NULLIF(btrim(...), '')`, and consider restricting the live fallback to `origin = 'external'`, or logging the anomaly.

### IN-03: The CSS spacing guard uses a denylist and does not enforce the scale

**File:** `tests/unit/Ui/AppCssScaleTest.php:19,51-56`
**Issue:** `FORBIDDEN_SPACING = [10, 12, 14, 18, 20]` lets through off-scale values such as 2, 6, 15, 22, 40px, and anything in rem or em. The failure message talks about the scale "4, 8, 16, 24, 32, 48, 64", which the test does not actually enforce.
**Fix:** Switch to an allowlist (`[0, 4, 8, 16, 24, 32, 48, 64]`) and flag any other integer px value.

### IN-04: The view guard heuristics miss some patterns and accept false passes

**File:** `tests/unit/Ui/ViewsLayoutGuardTest.php:49,87-90`
**Issue:** The inline-style check only matches `style="`, so `style='...'` slips through (single quotes are a CSP violation too). `testTablesAreResponsive` accepts any `table-responsive`/`dt-only-lg` class anywhere between the previous `</table>` and the next `<table`, even on an unrelated, already-closed element.
**Fix:** Match `style\s*=\s*["']`. For tables, check that the nearest unclosed ancestor `<div` carries the class, or keep the heuristic and document that it is best-effort.

### IN-05: The decision references for the date basis disagree

**File:** `app/Libraries/Export/YearArchive.php:21`, `app/Libraries/Reporting/ReportCalculator.php:18`, `app/Libraries/Reporting/BundleSelector.php:18`
**Issue:** The same turnover_date vs issue_date rule is cited as D-08 in YearArchive and as D-09 in ReportCalculator. This makes it harder to trace back to the decision log.
**Fix:** Use one decision id in all three docblocks.

### IN-06: An extra query runs to fetch the client name that the draft snapshot already has

**File:** `app/Controllers/InvoiceDelivery.php:446`
**Issue:** `$draft['invoice']` from `InvoiceMailer::draft()` already contains `snapshot` and `client_id`, and `TemplateContext` reads `snapshot['client']['name']` directly. The panel queries the database again for the same value, which is a second source for a value that should be identical.
**Fix:** Read the name from the decoded snapshot, and fall back to the query only when the name is empty.
