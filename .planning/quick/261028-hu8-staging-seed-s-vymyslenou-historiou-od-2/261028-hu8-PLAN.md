## Architecture (contracts for all tasks)

Namespace `App\Libraries\StagingSeed`. Code comments Slovak without diacritics (existing style), CLI/doc text Slovak with diacritics.

**Layers**
1. Pure planning (no DB): `Profile` + `Catalog` + `HistoryPlanner::build(Profile $profile, string $today, int $seed = Profile::SEED): HistoryPlan`. All randomness via `new \Random\Randomizer(new \Random\Engine\Mt19937($seed))` (deterministic across runs and PHP builds). No Faker (require-dev only, not in prod image), no `rand()/mt_rand()/random_*` and no wall clock inside the planner.
2. Application modules (DB, via the real application services only, never raw INSERT into business tables): each implements `SeedModule { public function name(): string; public function run(SeedContext $ctx): void; }`.
3. Orchestrator `StagingSeeder` with `public const MODULES = [Modules\AdminUser::class, Modules\MasterData::class, Modules\Tasks::class, Modules\Invoices::class];` (D-04: future modules Payments, Fx, CreditNotes, Limits append here). Runs `SeedGuard`, builds the plan, injects `SeedClock`, runs modules in order, prints per-module timing and final counts, restores the original clock in `finally`.

**HistoryPlan contract** (readonly arrays, string keys so modules map key -> DB id through `SeedContext::$ids`):
- `entities`: list of `{key: 'sk'|'cz'|'pl', country, currency (EUR/CZK/PLN), name_internal, active_from: '2026-01-01', version: <EntityService version array as in DevSeeder::version>, vat_regime (sk_non_vat / cz_non_vat / pl_exempt_113_1), doc_language, series_format (distinct valid SeriesFormat per entity, e.g. SK 'RRRRMM###', CZ and PL different valid formats), bank_accounts: list<{label, iban, swift, currency, is_default}>, later_versions: list<{valid_from, changes}>}`. SK gets one later version on 2026-07-01 (address change) so history crosses an entity version. PL also gets a non-default EUR account (DE89370400440532013000).
- `clients`: 8 entries, each with `entity` key and currency equal to that entity's currency (InvoiceGuards::assertCurrency; FX is Phase 8, so no cross-currency invoices yet): 3x SK domestic EUR (one with portal_name Taskman + portal_url_template 'https://taskman.example/task/{id}'), 2x CZ domestic CZK, PL domestic PLN, PL eu_b2b PLN (client in DE or AT with VAT id), PL non_eu PLN (client in CH or GB, doc_language en). Billing mode/regime combos MUST exist in legal_profiles from the migration. Each client has `first_month`, `cadence` ('monthly' | 'every_other' | 'quarterly_light'), `skip_last_full_month` (true for exactly one client: its previous month stays uninvoiced = late-invoicing scenario), `partial_months` (months with an extra mid-month invoice). Identifiers: fictional but VALID for ClientInput (compute NIP/IČO/IČ checksums or use known test values like NIP 5260250274), domains `.example`, emails `fakturacia@<name>.example`, rates as decimal strings.
- `tasks`: list of `{key: 'T0001'.., client, created_at (ISO datetime, working day 08:00-17:00 Europe/Bratislava), title (from Catalog fragments in the client's language), ticket (portal number or null), hours (estimate, multiple of 0.25 as string), rate (null = client rate, rarely an override), parts: list<{month 'YYYY-MM', hours, at ISO datetime}>, done_at: ISO|null}`. Last part of a done task is created by `TaskService::markDone(id, month, hours)` at `done_at`; earlier parts by `AllocationService::add` at their `at`. ~15% of tasks have 2-3 parts across consecutive months; a few in-progress tasks have parts but no done_at; some current-month tasks have no part yet.
- `invoices`: chronologically sorted list of `{key, at (ISO datetime 09:00-11:00), client, entity, month, issue_date = date(at), delivery_date, due_date, parts: list<array{task: string, index: int}>, kind: 'monthly'|'partial', payment_method: 'transfer'}`. Monthly: issue on first working day of month+1 plus a deterministic 0-3 working-day client offset, delivery = last day of month, due = issue + client due_days (entity default 14). Partial: issued on the 15th (next working day if weekend) of the month for the parts with `at` <= that moment; delivery = issue date. Events whose `at` would be after today are dropped (work stays uninvoiced). Current month is never invoiced.

**Profile** (`Profile::full()`, `Profile::small()`; `public const SEED = 20260101`): full = 3 entities, 8 clients, tuned so `HistoryPlanner::build(Profile::full(), '2026-10-28')` yields 130-170 tasks and 36-44 invoices (>= 3 partial). small = 3 entities, 3 clients (one per entity, monthly cadence, one with partial months), 2-3 tasks per client-month; used by the integration test with today frozen at 2026-03-20 (=> ~6-8 invoices).

**Clock** (`SeedClock extends Clock`, mutable: `at(string $isoDateTime): void`, `now()` returns the set instant in app timezone). The seeder reads `$today = service('clock')->today()` BEFORE injecting it (so tests can freeze today with FrozenClock), then `Services::injectMock('clock', $seedClock)`; every module calls `$ctx->clock->at(...)` before each service call so created_at, done_at, invoice created_at, document created_at and audit timestamps match the fictional history. Executor: confirm in vendor/codeigniter4/framework/system/Config/BaseService.php that `injectMock` is honored outside the testing environment (getSharedInstance checks `static::$mocks`); if not, add an equivalent override hook to `Config\Services::clock()` and say so in the SUMMARY.

**Issuing** (Modules\Invoices): for each invoice event in order, set clock to `at`, then
- monthly: `InvoiceDraftService::draft(clientId, month, entityId, issue, delivery, due)` -> assert `$draft->canIssue`, `$draft->partIds` equals the planned part ids (sorted), use `$draft->previewToken`;
- partial: compute the token for the subset exactly like tests/_support/IssueFixtures::previewTokenFor (InvoiceParts::unlocked filtered to subset -> SnapshotBuilder::build -> InvoiceCalculator::previewToken). Put this helper in the module as a private method (production code must not depend on tests/).
- `new IssueCommand(..., requestKey: deterministic UUIDv4 from the plan randomizer, confirmBackdate: false, userId: admin id, paymentMethod: 'transfer')` -> `InvoiceIssuer::issue()` with real renderers (inv-2 + rep-1, QR included). Chronological order across all entities means the backdate guard never fires; any IssueRejected aborts the seed with the reason and invoice key.
- Expected ≈0.6 s per invoice -> ~25 s for full profile.

**Admin** (Modules\AdminUser, first module, clock at 2026-01-01T08:00): `UserProvisioner::create(email, password, 'admin', 'sk', now)`; then enroll TOTP with the same UPDATE as TwoFactor controller (`totp_secret_enc = TotpService::encryptSecret(secret)`, `totp_enabled_at = now`, `totp_last_step = NULL`) — if no user_security row exists after provisioning, insert it the way the app does (read UserProvisioner). If the post-login flow forces backup-code setup when none exist, call `BackupCodeService::generate` and discard the codes (never print them). Must not send any mail and must not call SecurityNotifier. Do not log the password or secret.

**Credentials** (`SeedAdminCredentials::load(string $file, string $environment): self` with readonly `email`, `password`, `totpSecret`): parses KEY=VALUE lines (`SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `SEED_ADMIN_TOTP_SECRET`, `#` comments, optional quotes) WITHOUT putting them into the process env. File path from `Config\Staging::$adminFile` (default `/run/secrets/seed_admin.env`). If the file is missing: in `production` -> refuse; in development/testing -> fall back to `env('SEED_ADMIN_EMAIL')` etc. from dev .env (D-02 dev fallback); still missing -> refuse with a message naming the keys. Validate: email filter, password non-empty (UserProvisioner enforces policy), TOTP secret base32 `[A-Z2-7]{32,}` after stripping spaces/`=`. Exception messages never contain values.

**Guards** (`SeedGuard`, throws `SeedRefused` with a reason code; each check independent):
1. `Config\Staging::$seed === true` (CI4 env key `staging.seed = true`, only in staging app.env; default false).
2. Host of `config(App::class)->baseURL` is not in `SeedGuard::PRODUCTION_HOSTS = ['work-tracker.vostack.dev']` (case-insensitive, trailing dot stripped).
3. Database is pristine: zero rows in `invoices`, `entities`, `clients`, `tasks`, `users` (production always has data). Queried with the seed connection.
4. Admin credentials load (production without the secrets file refuses).

**DB role** (D-05 decision): the seed connects with the `default` group = app_rw from app.env, exactly like php-fpm. Everything goes through application services that already work as app_rw (UI and spark user:create do), so missing grants surface on staging as they would in production, and the app_owner password stays only in migrate.env. Drop/provision is done by the db container as superuser (same as db-reset.sh), migrations stay in `migrate` (app_owner). Same encryption.key as php-fpm (same app.env) so the stored TOTP secret decrypts at login.

**Failure semantics**: not one big transaction (each service call is its own transaction like in the UI). On failure the command exits non-zero, deploy.sh stops before `up` (old containers keep running against a partially seeded DB) and the next deploy resets again. Documented.

**Pre-migration backup on staging**: kept unchanged (D-01 "your call"): the production code path stays identical, the dump of synthetic data is cheap (seconds, rotation 14), and if a guard ever misfired a verified dump exists. Reset happens AFTER the backup.
</design>
